# 需求分类、适度拓展与完成判断

## 先确定需求，再选择执行线路

按用户想要改变的行为、对象和验收条件建立简短需求ID。一个需求可跨很多轮，一条消息也可能同时修改多个需求。相同模块中不同目标可以分开；共同成因只是待查假设，不因标题相同就合并。保留活跃需求的已确认条件和待查项，“继续”恢复当前活跃项，不恢复已取消的方案。

| 类别 | 先做什么 | 交付与验收重点 |
| --- | --- | --- |
| 故障修复 | 重现触发路径，区分环境、版本、平台与症状；查证根因 | 修复具体行为并回归相邻路径，不能以编译通过替代体验验收 |
| 新功能 | 确认用户流程、输入输出、数据状态和失败处理 | 连通端到端操作，检查权限与兼容性 |
| 重构/规范 | 理解现有职责和调用方，标明需保持的行为 | 复用与迁移一致，覆盖入口和存量数据，不顺便替换技术栈 |
| 性能优化 | 同条件采样，拆分网络、存储、渲染与交互成本 | 比较基线与改后结果；未测收益不承诺，不把不同缓存当同一数据 |
| 设计/方案 | 学习参考的具体机制，形成适合当前产品的一致方案 | 用户只要方案时先交付方案；示例是意图锚点，不强行按口头猜测精确复刻 |
| 调研/评审/教学 | 明确对象、资料角色和证据范围 | 解释或报告，不擅自落地代码 |
| 部署/打包/PR/清理 | 确认制品、目标端、发布边界和可恢复性 | 区分代码完成、可用制品、外部提交、用户实测，不漏已授权目标端 |
| 文稿/图片/演示等产物 | 明确真实产物及适用领域流程 | 使用领域技能交付，不能把生成prompt当作业务完成 |

复合请求采用主类别加必要子任务，不为分类本身反复询问。执行prompt可只写“需求R3：修复切页闪烁；补充R2：桌面制品”，无须每轮输出整张表。

## “等”表示同类拓展，不表示无限授权

提取用户列举项共有的目标，再检查实现该目标所需的相邻机制。分开列出明确要求、合理拓展、暂不纳入项；拓展需有理由和来源，不伪装成用户原话。

- 用户说“事件注销、定时器等内存泄漏风险”：检查相关订阅、observer、取消中的异步请求及缓存页面的激活/停用，依据项目技术栈和实际资源生命周期筛选，不直接引入全新架构。
- 用户说“动画、滚动等体验问题”：检查进入/返回/中断、加载与失败状态、长列表及跨端共用组件，优先真实路径和证据，不仅改给出的按钮。
- 用户说“方案：XX等”：方案阶段可研究同类替代与取舍；只获准给方案时，合理拓展仍不代表获准部署、付费或破坏性改动。

先读代码、项目规则和已有证据；涉及陌生机制、版本差异或竞品行为时，使用适用的检索/分析工具，优先官方文档与源项目。找到对当前目标有解释力的证据即可收敛，不漫无目的研究所有竞品。外部最佳实践是候选依据，不证明本项目已有该缺陷。用户明确“仅这些”时不额外落地。

参考：[Vue资源清理与生命周期](https://vuejs.org/api/composition-api-lifecycle.html#onunmounted)、[Vue性能分析与大列表](https://vuejs.org/guide/best-practices/performance.html)。这些是示例依据，不把Vue用作所有项目的技术前提。

## 减少的是可避免返工，而不是所有对话

对每项需求记录：类型、目标、有效约束、必要拓展、状态、证据来源、下一步。标记消息是初始请求、澄清、遗漏纠正、新范围、方案批准、验收反馈还是状态询问。新需求和合理取舍不算agent误解；重复纠正同一已明确条件才是可避免返工的信号。不能从聊天轮数推断修改次数，实际交付尝试只计有产物证据的轮次。

区分结果状态：

- 用户明确实测认可：只接受其认可的具体行为或平台，不推及全部需求。
- 用户说“方案没问题/开始做”：是执行批准，不是成果满意。
- 用户指出仍有问题：按对应需求重开，并记录症状、触发路径和未满足条件。
- 只有agent声称完成、用户换话题或沉默：验收未知，不能标成功。

同一问题多次未解时，停止沿用未经证实的猜因；先恢复约束、检查上次漏测路径、确定区分假设的观察，再决定是否需要具体问题。不以同义改写prompt或反复打包增加“完成次数”。目标是以尽量少的可避免交付轮次满足有效要求，而不是跳过测试、澄清或必要迭代。
